# 离线交互应用

2026-11-07新增于现有仓库。`web/`包含原生HTML/CSS/classic JS，`dist/`由明确白名单复制构建，六文件ZIP根入口为`index.html`。没有框架、外部素材、网络依赖、支付或运行时模型调用。

## 可操作流程

1. 录入新批次：数量、单位、已知过敏标签、标签日期/原文、可选包装日期/来源、开封时刻/记录，以及标签明确写的开封后小时数。新批次不默认勾本人核查。
2. 展开来源并核查：缺日期、同类日期冲突、仅包装日期、未来记录、开封说明缺失、已过输入时限、未确认或用户排除均阻断。勾选确认不能覆盖这些门禁。修正当前转录保留旧来源，核查不能改余额和食材身份。
3. 新增或编辑自己的菜谱、各食材用量、已知过敏标签、每份估计成本与来源。单位随库存，不隐式换算克/毫升/个。
4. 应用份数、估计预算、排除项与简单菜优先偏好。候选解释批次分配、可分配不足与实物缺口；待核查实物不自动视为必须购买。每道菜是独立预览，未预留库存。
5. 审阅批次、用量、份数、估计成本和来源，明确勾选后确认。确认时重新核对当前设备时间与完整库存/来源/菜谱/偏好快照；变化或到期就使原审阅失效。整笔通过才扣减。
6. 查看回执、刷新恢复、导出。相同消费键/意图只恢复原回执。只能撤回最近一笔且其后没有修改的记账，原回执保留为已撤回；不代表恢复实物。
7. 导入Python v1项目或浏览器导出，以当前库存/估计开启新账本。旧回执作为导出附件留存，不作为可信历史回填；不导入待执行批准。

成本来自用户估计，不是实时价格、采购、支付或营养计算。全部来源是用户输入，不是系统独立核实。日期与本人确认均不能证明食物安全。

## 与Python的关系和差异

纯JS移植既有日期/来源门禁、最早录入约束优先分配、精确数量、用户标签过滤及实物缺口。共享`examples/pantry.json`在Node测试中与真实Python `plan_project`逐菜比较分配/阻断/缺口。Python CLI、HTTP、SQLite和模型适配器未修改，原26项测试通过。

份数、整数分成本估计与预算、简单菜排序、审阅快照及最近一笔撤回位于浏览器状态外层，没有塞入Python严格项目schema。

- 数量用整数千分位、最多三位小数；金额用整数分。浏览器时间为毫秒精度，不能声称与Python微秒边界完全一致。IANA时区由浏览器Intl提供，不保证各浏览器历史时区数据版本一致。
- 浏览器标签用JS小写后精确匹配，须保持相同拼写；没有完整移植Python全部Unicode casefold。它不能识别未标注成分、交叉接触或医疗禁忌。
- 本地JS账本不是SQLite事务或服务器鉴权，仅供本人单标签使用。检测其他标签改动时取消审阅并要求重载，但不承诺跨标签原子性、多用户隔离或防篡改。
- 回执一致性会重算已绑定快照的before/used/remaining，不信任导入数字；这是损坏检查，不是数字签名或实物证明。

## 保存与容量

localStorage权限/配额异常时降级为内存并提示导出。损坏保存不用于扣减，清除后新示例仍可保存。返回页面会取消原审阅，确认时另行重核时钟。

文件按UTF-8字节限制1MB，拒绝重复键、非有限数字、深度超过40、未知项目字段、无效来源与数量。核心可恢复状态最多900,000 UTF-8字节，外层写入另有950,000字节保护。消费/修改/撤回超限时在写入前失败，原库存保持不变。完整快照占空间；大量冗余来源可能提前到上限，应导出留存、减少冗余后开启新账本。
